# 規格驅動開發流程

採用類似OpenSpec的輕量流程；目前未安裝OpenSpec CLI，不能宣稱已導入該工具。

## 正式規格

requirements.md、tenancy-and-parking.md記錄業務規則；mobile-design.md為畫面與模型草案。變更以最新明確使用者決定為準，衝突時先更新規格。

## 每項變更

在 docs/changes/<功能名>.md 記錄：
1. 要解決的問題、範圍與不含項目。
2. 畫面及資料影響，包含舊資料相容與更新方式。
3. 可勾選開發任務。
4. Given/When/Then驗收案例與實際測試結果。
5. 已知限制、完成狀態與對應commit。

流程：規格→任務→coding→review→驗收→更新完成紀錄。一般實作選擇由開發者決定；需要改變業務行為或由使用者選擇的視覺方案先討論。並非每個commit都要求使用者批准。

## Review檢查

由GPT統一開發並另行檢查差異、金額計算、重複入帳、租約隔離、起算餘額、同步重試、憑證位置、升級與資料保存。此為同一開發者自我審查，不宣稱獨立Claude review。

## 完成條件

- 已實作驗收行為，相關測試與Android lint通過。
- GitHub Actions編譯成功、APK已存在；CI成功不代表已實機驗證。
- 正式可記帳版本需備份/還原及固定簽署更新驗證。
- 未完成的Google同步、拍照與語音明確顯示未啟用；不以假成功替代。
